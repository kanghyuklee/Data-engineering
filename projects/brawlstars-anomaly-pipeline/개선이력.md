# 트러블슈팅 · 개선 이력

> 개발하면서 받은 리뷰 피드백과 실제로 겪은 장애를 어떻게 진단하고 고쳤는지 기록.
> 각 항목 = **문제 → 원인 → 조치 → 효과**. 안정적인 파이프라인(유실·중복 없이, 추적 가능하게)이라는 목표에 맞춰 정리.

---

## 1. 리뷰 피드백 → 조치

| 피드백 (지적) | 왜 문제였나 | 조치 | 효과 |
|---|---|---|---|
| **승부조작 집계에 친선전이 섞인다** | 친선전·토너먼트는 상대를 직접 고를 수 있어 "같은 상대 반복"이 당연 → 승부조작 신호가 오탐으로 쏟아짐 | 집계 대상을 **매칭전(ranked·soloRanked)만**으로 필터 (`preprocess.py`). Parquet 원본은 전부 보존 | 승부조작 의심 **105 → 11건**으로 축소, 오탐 제거 |
| **opponents에 내 팀원이 섞인다** | "나 빼고 전부"를 상대로 넣으니 팀원이 opponents에 포함 → 승부조작(상대 반복) 신호가 뭉개짐 | `owner_tag`가 속한 팀 → `teammates`, 나머지 팀 → `opponents`로 **팀 기준 분리** (`producer.py`) | 승부조작(상대 반복)·팀 어뷰징(팀원 반복)을 분리 분석 가능 |
| **overwrite가 테이블을 날린다** | Spark `mode("overwrite")`는 테이블을 DROP 후 재생성 → `schema.sql`의 PK·인덱스가 매 실행 사라짐 (문서-코드 불일치) | 1차: `option("truncate","true")`로 TRUNCATE+INSERT(정의·인덱스 보존). 2차: **staging + `ON CONFLICT` UPSERT**로 전환 | 인덱스 유지 + 배치에 없는 계정·ML 컬럼까지 **누적 보존**, 조회 무중단 |
| **불량 데이터가 조용히 사라진다** | `dropna`로 버리면 무엇이 왜 빠졌는지 알 수 없음 → 유실·관측성 문제 | **DLQ 라우팅** — 유효/불량 분리, 불량은 원문·사유와 함께 `bs.dlq`로 격리 + `입력 = 정제 + DLQ + 중복` 등식 검증(`assert`) | 깨진 60건 주입 시 **DLQ 45 격리·유실 0** 실측 |
| **`count()` 반복 = Kafka 반복 읽기** | Spark `count()`·`write`는 action이라 캐시 없으면 매번 Kafka 재읽기 → 브로커 부하·느림 | 읽은 DataFrame에 **`.cache()`** (Kafka 1회만 읽기) | 여러 action이 Kafka를 1회만 스캔 → 전처리 시간·브로커 부하 감소 |
| **`lastProgress`·`maxOffsetsPerTrigger`를 보라** | 둘 다 streaming 지표인데 우리는 배치 구조 | 배치 트레이드오프는 유지하되, 로드 테스트는 **셔플 파티션 튜닝**으로 대응(아래 3절) | 측정 가능한 개선 지표 확보(전후 비교표) |

## 2. 장애·에러 진단 → 해결

> 태도: 실행 위치 · 접속 주소 · 오류 메시지 · 시도한 내용을 **함께** 본다.

| 증상 | 진단(어떻게 조회) | 원인 | 해결 |
|---|---|---|---|
| 대량 수집 중 `ReadTimeout`(SSL handshake) → 크롤 전체 중단 | 스택트레이스 + "411명 저장 후 종료" 로그 | 네트워크 일시 타임아웃을 **재시도 안 함** → 1건 실패에 크롤 전체 종료·대기 큐 유실 (**단일 실패점**) | `_get`에 timeout·연결오류 **backoff 재시도**(소진 시 그 태그만 skip) + `crawl` **재실행 이어받기**(디스크에 있으면 API 재호출 없이 큐만 확장) |
| 수집이 초당 1건 | 처리량 측정 | `requests` 동기·단일 스레드라 왕복(RTT) 대기가 병목 | `ThreadPoolExecutor`로 **동시 요청** + rate limit을 `Lock`으로 스레드 안전화(전체 속도는 `--rps` 상한=429 예방) → **≈10배** |
| `detection_result`에 PK·인덱스 없음 | `\d`·`pg_indexes`로 확인(0 rows), 타입이 Spark 추론형 | 과거 truncate 없는 overwrite가 테이블을 DROP·재생성 + `pgdata` 볼륨 유지로 schema.sql 재실행 안 됨 | `DROP TABLE` → `psql -f schema.sql`로 재생성 후 재적재. **유지 조건 = 테이블은 schema.sql産 + Spark는 항상 truncate=true** |
| Airflow `spark_preprocess` 간헐 실패 | task 로그: `FileNotFoundException: .../_temporary/... does not exist` | 프로젝트가 **OneDrive 동기화 폴더** → Spark `_temporary` rename 중 동기화가 파일을 건드림 | SparkSession에 `fileoutputcommitter.algorithm.version=2`(최종 경로 직접 커밋) + **retry가 일시 실패 흡수**(안정성 설계 실증) |
| Airflow 이미지 `numpy dtype size changed` ABI 오류 | import 스택트레이스 | 이미지 pandas가 numpy1로 빌드됐는데 numpy2 설치됨 | `pip install "numpy<2"` 고정 |
| Airflow 웹서버 부팅 루프 | "No response from gunicorn master within 120s" 반복 | Windows Docker 파일시스템이 느려 워커 부팅이 120초 초과 | `WEB_SERVER_*_TIMEOUT=300` · `WORKERS=2` → ~35초 기동 |
| Airflow 날짜가 계속 UTC | UI·DAG 비교 | 기본 타임존 UTC | `DEFAULT_UI_TIMEZONE=Asia/Seoul` + `start_date`를 `pendulum ... tz="Asia/Seoul"`로 (내부 저장은 UTC 유지) |
| `bitnami/spark` pull 실패 | compose 로그 "not found" | 이미지가 Docker Hub에서 내려감 | 공식 `apache/spark:3.5.3`으로 교체 |
| `spark-submit: not found` / Ivy `FileNotFoundException` | 컨테이너 안 경로·스택트레이스 확인 | PATH 미설정 / 비root 유저 `.ivy2` 쓰기 권한 없음 | 전체 경로 `/opt/spark/bin/spark-submit` + `--conf spark.jars.ivy=/tmp/ivy` |
| Spark 컨테이너가 Kafka 접속 실패 | 실행 위치 vs 접속 주소 점검 | `localhost`는 컨테이너 자신 | 리스너 2개 — 호스트용 `localhost:9092` + 컨테이너용 `kafka:29092` |
| `/opt/...` 경로가 `C:/...`로 바뀜 / 한글 깨짐 | 변환된 경로·콘솔 출력 확인 | Git Bash 경로 자동변환 / cp949 | `MSYS_NO_PATHCONV=1` · `PYTHONUTF8=1` |
| 토픽 메시지가 계속 누적 | `kafka-get-offsets.sh`로 오프셋 확인 | 컨테이너 restart는 데이터 유지(볼륨 없음) | 토픽 delete→recreate로 초기화 후 재적재 |
| `git push` rejected(non-fast-forward) | `git status`·원격 비교 | 원격에 다른 커밋 존재 | `fetch → rebase → push` 패턴 |

## 3. 성능·안정성 개선 (측정 기반)

| 개선 | 방법 | 효과 |
|---|---|---|
| **전처리 속도** | `spark.sql.shuffle.partitions` **200 → 8** (로컬에서 수만 건을 200조각으로 나누면 조각 비용 > 실계산) | 전처리 **~98초 → ~88초 (≈11%↓)**, 각 2회 측정 |
| **진짜 병목 제거** | 셔플은 전체의 일부(암달의 법칙) → 진짜 병목은 **중복 11배 재처리**. Kafka 70만 중 고유 6만 → DAG에서 fetch 제거(리플레이만) + 토픽 리셋 | 입력 자체를 1/11로 축소 — 처방 중 효과 최고 |
| **저장 증분화** | overwrite+truncate → **staging + `ON CONFLICT (player_tag)` UPSERT** | 배치에 없는 계정·인덱스·ML 컬럼 보존, 조회 무중단, backfill에도 2배 안 됨 |
| **날짜별 백필** | `target_date` 파라미터 + Parquet `partitionOverwriteMode=dynamic` | 지정 날짜만 재처리(다른 날짜 파티션 보존) |
| **수집 처리량** | 동기 단일 스레드 → `ThreadPoolExecutor` 동시 요청 | 초당 1건 → ≈10배 |

## 핵심 교훈

- **에러 없이 조용히 일어나는 문제**(유실·중복·매번 재처리)가 가장 위험 — `입력 = 정제 + DLQ + 중복` 같은 **등식으로 드러낸다**.
- 개선은 **가설 → 한 번에 하나만 바꾸기 → 같은 조건 재측정**. 바꾸기 전 숫자를 남긴다.
- "이미 있으면 건너뛰기"는 다시 돌릴 수 있는 구조가 아니다 — **날짜 단위 덮어쓰기 + event_id 멱등**으로.
- 품질 검사는 적재 뒤가 아니라 **게시 전**에 — 틀린 결과가 밖으로 나가지 않게.
